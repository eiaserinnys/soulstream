# 인바운드 웹훅 경로 지도

인바운드 웹훅은 외부 서비스가 `POST /api/hooks/<grant_id>`로 보낸 자료를 소유자의 세션 입력으로 접수하고, `GET /api/hooks/<grant_id>/requests/<request_id>`로 그 접수 상태를 조회한다. 헤더를 붙일 수 없는 서비스는 키 방식 웹훅의 `POST /x/<key>/hook`으로 같은 접수를 하며, 그때 URL의 키가 유일한 자격이다. 상태 조회는 `/x`가 아니라 `/api/hooks`와 관리 API로 한다(키 방식을 발급한 경우 Bearer 키로 같은 조회를 쓴다).

| 단계 | 파일:심볼 | 이 단계가 소유한 사실 |
| --- | --- | --- |
| 1. 수신 | `orch-server-ts/src/webhooks/inbound_hook_routes.ts:registerInboundHookRoutes` | 플러그인 범위에서 content-type 파서를 전부 지우고 `*` 파서를 `parseAs: "buffer"`, `bodyLimit: INBOUND_HOOK_MAX_BODY_BYTES`(256 KiB)로 다시 붙인다. 본문은 항상 원시 바이트로 받으며, `Content-Type`이 없어도 빈 media type 경로로 `*` 파서에 도달해 같은 원시 바이트가 된다. 라우트 자체 `bodyLimit`도 같은 값이라 초과분은 파서에서 413 `FST_ERR_CTP_BODY_TOO_LARGE`가 되고, 플러그인 `setErrorHandler`가 413/415/400/503을 정규화한다. `onSend`가 모든 응답에 `cache-control: no-store`를 붙인다. |
| 2. 두 인증 | `inbound_hook_routes.ts:selectCredential`, `orch-server-ts/src/external_access/external_access_grant_repository.ts:resolveInboundWebhookGrant` | 1) `webhook-signature` 헤더가 있으면 서명 모드: `standard_webhook_signature.ts:verifyStandardWebhookSignature`가 `whsec_` 비밀키로 `${id}.${timestamp}.` + 원시 본문 바이트의 HMAC-SHA256을 검증한다(300초 허용, `v1,<base64>` 목록 중 하나 일치, `timingSafeEqual`). 2) 없으면 `Authorization: Bearer <ssxw_ 키>`의 키 모드: URL의 grant id와 키에 인코딩된 grant id가 같아야 한다. 둘 다 없으면 401. 3) 공통 판정(`judgeGrantAccess`)이 kind=`inbound_webhook`, `auth_mode` 일치, 폐기·만료·발급자 승인·대상 세션 ACL·필요 권한(`send`/`read_own`)을 검사하며, 어떤 자격 실패든 같은 본문의 401로 답한다. |
| 2a. 헤더 없는 수신 | `inbound_hook_routes.ts` `POST /x/:key/hook`, `external_access_grant_repository.ts:parseExternalAccessKey`, `resolveInboundWebhookGrant` | 키 방식 웹훅의 grant를 URL 키로만 찾는다: `parseExternalAccessKey(key)`가 grant id를 꺼내면 `resolveInboundWebhookGrant(grantId, {mode:"key", rawKey:key}, "send")`가 2번과 같은 판정(kind=`inbound_webhook`, `auth_mode`, 해시 상수 시간 비교, 폐기·만료·발급자·대상 세션 ACL·`send`)을 한다. 판정을 복사하지 않으므로 링크 키(`ssxl`)·서명 방식·틀린 키·해석할 수 없는 키·폐기·만료는 모두 같은 401 `{error:{code,message}}`이고 영수증을 만들지 않는다. 요청의 `Authorization`과 `webhook-signature` 헤더는 이 경로에서 보지 않는다. 본문 계약·멱등·접수·오류·202는 `receiveInboundHook` 하나를 `/api/hooks/:grant_id`와 함께 쓰고, 이 라우트만 `referrer-policy: no-referrer`를 더한다(파서·413·`cache-control: no-store`는 같은 플러그인 범위). 로그 경로는 `/x/:key/hook`이며 키는 남기지 않는다. |
| 3. 멱등 키 순서 | `inbound_hook_routes.ts` POST 핸들러, `requestIdOf`, `sha256Hex` | 요청 id는 `webhook-id` 헤더 → `Idempotency-Key` 헤더 → JSON 본문의 `request_id` 순으로 고른다. 요청 해시는 항상 원시 본문 바이트의 sha256이라 같은 id라도 본문이 다르면 `external_input_receipts`의 PK(grant_id, request_id) 충돌로 409다. 같은 id·같은 바이트는 저장된 접수를 그대로 돌려주며 `preamble`을 고쳐도 이미 저장된 입력 본문은 바뀌지 않는다. 형식이 틀린 요청 id는 400이다. |
| 4. 본문 구성 | `inbound_hook_routes.ts` POST 핸들러, `orch-server-ts/src/external_access/external_input_service.ts:externalInterventionBody`, `externalSenderContextItem` | 원시 바이트를 UTF-8 strict로 디코드하고(실패는 415 `unsupported_encoding`, 비UTF-8 본문을 텍스트로 바꾸지 않는다), `application/json`이면 `text` 필드, 아니면 본문 전체를 메시지 텍스트로 쓴다. 빈/공백 텍스트는 400 `empty_body`. 최종 입력은 `preamble ?? defaultInboundWebhookPreamble(label)` + 빈 줄 + 텍스트이며, `material_body: true`로 `body_disposition`(본문은 지시가 아니라 자료라는 문장)을 caller context에 넣는다. `caller_info`는 source=external, transport=webhook, user_id=null로 고정된다. |
| 5. 접수와 전달 | `external_input_service.ts:admit`, `createExternalInterventionDispatch` | receipt와 전달 원장을 한 transaction으로 쓰고 커밋 뒤 `executeSessionIntervention`으로 전달한다. 전달이 실패해도 접수는 durable하며 202 + 경고 로그로 남는다. 버킷 소진은 429 + `Retry-After`다. |
| 6. 상태 조회 | `inbound_hook_routes.ts` GET 핸들러, `external_input_service.ts:readExternalRequestStatus` | `GET /api/hooks/<grant_id>/requests/<request_id>`는 같은 두 인증으로 grant를 해석하고 `read_own`을 요구한다. 같은 grant의 접수만 200으로 돌려주며 다른 grant의 요청은 404다. |
| 7. 버킷 | `external_input_service.ts`, `orch-server-ts/src/external_access/external_access_token_bucket.ts` | `production.ts`가 `ExternalAccessTokenBucket` 하나를 만들어 `ExternalInputService`에 넣는다. grant별 in-memory 버킷으로 수신은 분당 30회(`Retry-After: 2`), 상태 조회는 분당 120회(`Retry-After: 1`)다. |
| 8. 라우트 등록과 계약 | `orch-server-ts/src/app.ts`, `orch-server-ts/src/production.ts`, `orch-server-ts/src/contract/route_coverage_matrix.ts` | `createApp`의 `inboundHookRoutes` 옵션으로 등록하고 `production.ts`는 `externalAccessGrants`와 `runtime.sessionActionCommandRoutes`가 있을 때만 서비스를 만든다. 세 라우트 모두 인증 없이 라우트 안에서 자격을 판정하므로 라우트 커버리지 행렬의 `webhooks.inbound` owner에 `false`로 등재하고(`POST /x/:key/hook` 포함), TS 전용 키 세 개를 `tsOnlyRouteKeys`에 둔다(`POST /x/{key}/hook`). |
| 9. 관리 API 발급 | `orch-server-ts/src/webhooks/inbound_webhook_routes.ts:registerInboundWebhookRoutes`, `external_access_grant_repository.ts:issueInboundWebhook` | `POST /api/webhooks/inbound`는 로그인(`currentEmail`)과 대상 세션 ACL(`SERVICE_CALLER` + 로그인 email)을 확인한 뒤 grant를 발급하고 201과 `Cache-Control: no-store`로 `{id, url, auth_mode, secret, label, target_session_id, preamble, created_at, expires_at}`을 낸다. `url`은 공개 주소 + `/api/hooks/<id>`이고, `secret`은 key 방식이면 `ssxw_` 키, signature 방식이면 `whsec_` 비밀이며 이 응답에서 한 번만 나온다. key 방식 응답에는 `key_url`(공개 주소 + `/x/<secret>/hook`, `buildInboundWebhookKeyUrl`)이 함께 오고 서명 방식에는 그 칸이 없다. 목록·폐기·요청 목록 응답에는 `key_url`도 키도 싣지 않는다(저장소에 원문 키가 없다). 본문은 strict라 모르는 필드는 422, label은 trim 1~80자, preamble은 null 또는 4000자까지, `expires_in_seconds`는 null 또는 60~315360000이다. 없는 세션과 접근할 수 없는 세션은 같은 404이고 grant를 만들지 않는다. |
| 10. 관리 API 목록 | `inbound_webhook_routes.ts`, `external_access_grant_repository.ts:list`, `external_input_service.ts:summarizeGrants` | `GET /api/webhooks/inbound`는 로그인 사용자의 `kind=inbound_webhook` grant만 created_at 내림차순으로 낸다(같은 사용자의 링크 grant는 빠진다). 항목은 `{id, label, target_session_id, auth_mode, preamble, url, created_at, expires_at, revoked_at, last_used_at, state, recent}`이고 `state`는 revoked_at이 있으면 `revoked`, 아니고 expires_at이 지났으면 `expired`, 아니면 `active`다. `recent`는 목록 전체에 한 번의 조회로 낸 grant별 `{count_24h, failed_24h, last_received_at}`이며 count_24h는 최근 24시간 영수증 수, failed_24h는 그 가운데 원장 `aggregate_state='dead_letter'` 수, last_received_at은 가장 최근 영수증 시각(없으면 null)이다. 비밀(key_hash, signing_secret)은 어느 응답에도 싣지 않는다. |
| 11. 관리 API 요청 목록 | `inbound_webhook_routes.ts`, `external_access_grant_repository.ts:findOwned`, `external_input_service.ts:listRecentRequests` | `GET /api/webhooks/inbound/:id/requests?limit=`은 id가 uuid가 아니면 422, limit이 1~50 정수가 아니면 422이고 기본 20이다. 로그인 사용자 소유의 `kind=inbound_webhook` grant가 아니면(남의 것, 링크 grant, 없는 id 모두) 같은 404이고, 폐기·만료된 웹훅의 기록도 읽는다. 200 `{items}`의 항목은 상태 조회(`readExternalRequestStatus`와 같은 `externalRequestStatus` 판정)에 `received_at`(영수증 created_at, ISO)을 더한 모양이며, 영수증·원장·세션·회신을 한 SQL로 newest first로 읽는다. |
| 12. 관리 API 폐기 | `inbound_webhook_routes.ts`, `external_access_grant_repository.ts:revoke` | `DELETE /api/webhooks/inbound/:id`는 `revoke(email, id, "inbound_webhook")`로 그 kind의 행만 폐기하고 200과 목록 항목 모양(recent 제외)을 낸다. 남의 것, 링크 grant, 없는 id, 이미 폐기된 것은 모두 404이고, 링크 grant의 `revoked_at`은 이 경로로 바뀌지 않는다. `revoke`의 kind 인자는 선택이라 넘기지 않는 링크 관리 경로는 지금과 같은 동작이다. 폐기 뒤 같은 자격의 수신은 401이다. |
