# Portable node connect

## Request path

A public shallow clone of `eiaserinnys/soulstream` is the only input. `portable-node/start.sh` (Windows: `portable-node/start.cmd` → `bootstrap.ps1`) reads `portable-node/runtime-lock.json`, downloads the pinned Node archive for the current platform, verifies its `sha256`, extracts it under `portable-node/.state/runtimes/node/<version>/<platform>`, writes the same `.portable-runtime.json` install record the launcher writes (`kind`, `version`, `sha256`, `installed_at`), copies `launcher.mjs`, `defaults.json`, `lib/`, and `config/` to `.state/boot`, and starts the launcher with that Node. A different lock version installs into a new version folder; neither the bootstrap nor the launcher deletes a runtime folder it is currently executing from. The launcher checks the lock again on every re-entry signal (exit code 75). The shim relaunches on 75 without an attempt cap; repeated re-entry with the same reason and key (`reentry.json`) is stopped by the launcher as an error, not by the shim.

On first run `lib/pairing.mjs` asks for `node_id` only, calls `POST /api/node-pair/start` with a fixed `company_pc: false` (the pairing API requires a boolean), prints the user code, and polls `POST /api/node-pair/poll` until approval or `expires_at`. The node name must match P1's `^[a-z0-9][a-z0-9-]{1,62}$`; the default slug from the hostname is trimmed into that rule and falls back to `portable-node`. The approved token is written to `.state/node.json` and is never printed.

`lib/release.mjs` fetches `GET /api/node/releases/current` with the node bearer, compares `source_commit` with the checkout HEAD, and on a mismatch fetches only that SHA and detaches the checkout while `.state/` stays ignored. It then downloads the pinned runtime archives and the payload. The bundle is checked against its `sha256` (the launcher strips the `sha256-` prefix before comparing the downloaded bytes), inspected before extraction for absolute paths, `..`, symlinks, and hard links (runtime archives allow relative links that resolve inside their own folder), extracted to a temporary directory, validated against the P3 metadata (`sha256-<hex>` digests, exact metadata/file keys, required artifact list, no unlisted files, no links), bound with `bind-release.mjs`, and moved to `.state/releases/<source_commit>`. The verified marker lives outside the payload at `.state/releases/<source_commit>.verified.json`. The P3 payload keeps `main.js` at the release root and the runner artifacts under `runner/`; `SOUL_RUNNER_ARTIFACT_DIR` points at `<release>/runner`.

`lib/config.mjs` writes the executor default config generation (see below) under `.state/config/<generation>` and builds the child environment file. The launcher creates `<stateRoot>/workspace` as an empty folder if it is missing; this is the agent workspace root (`.state/workspace`, with `.projects` under it) and nothing is cloned or fetched into it. `lib/git.mjs` only aligns the source checkout to the release commit and sets `GIT_CONFIG_GLOBAL` for its own git child processes.

Codex runs `codex login --device-auth` against `CODEX_HOME=.state/codex` with `cli_auth_credentials_store = "file"` when login is missing; its child environment contains only `CODEX_HOME`, the home/temp/XDG paths, and OS execution keys, never the soul-server prepared env or parent secrets. Claude is not logged in by the launcher; the terminal points at the existing dashboard node login location. `lib/supervisor.mjs` starts `soul-server-ts` as the foreground child with the explicit environment contract from `lib/environment.mjs`. Git child processes get a minimal environment (`PATH`, OS keys, home/temp, `GIT_CONFIG_GLOBAL`), not a copy of the parent environment.

## Release delivery routes

`GET /api/node/releases/current` answers with the commit this orchestrator serves (the same source as the health `build_id`) plus `sha256-<hex>`, `size`, and `download_path`, read from `<PORTABLE_NODE_RELEASES_DIR>/<source_commit>/node.tar.gz` and `node.tar.gz.sha256`. Those files are written by the deploy hook: `deploy/haniel/build-core.sh` runs `deploy/haniel/pack_portable_node_release.sh` at the end of a successful build when `PORTABLE_NODE_RELEASES_DIR` is set. It packs a clean shared clone of the deployed commit into `<PORTABLE_NODE_RELEASES_DIR>/<source_commit>/`, skips a commit that is already packed, keeps the three newest commit folders plus the just-published one, and only warns when it fails. `GET /api/node/releases/:source_commit` streams that gzip with `Content-Length` and `Cache-Control: no-store`. Both routes require a node credential: the shared service bearer gets `403 NODE_CREDENTIAL_REQUIRED`, and missing or revoked tokens get `401`. Without `PORTABLE_NODE_RELEASES_DIR` both answer `503 PORTABLE_RELEASES_DISABLED`; a serving commit with no packed files answers `503 PORTABLE_RELEASE_NOT_READY` and never falls back to an older release. A commit outside `^[0-9a-f]{40}$` is `400`; an absent file is `404`.

## Executor default config

`portable-node/config/` holds the four templates the executor reads from its own folder: `agents.yaml`, `model-catalog.yaml`, `mcp-registry.yaml`, and `mcp-profiles.yaml`. On first run and on every switch staging `lib/config.mjs` substitutes two placeholders — `__STATE_ROOT__` becomes the state root and `__SOUL_HOST_PORT__` becomes this run's `MCP_INTERNAL_PORT` — and writes the result under `.state/config/<generation>/`. The generation name is `local-` plus the first 12 hex characters of the sha256 over the four pre-substitution template contents, so the same templates rewrite the same folder; a restart that allocates a new MCP port replaces the old port there.

The default config declares two agents, `claude-default` (Claude, preset `claude-opus`) and `codex-default` (Codex, preset `codex-6.1-sol`), both with workspace `__STATE_ROOT__/workspace` and the `portable-default` MCP profile. That profile contains exactly one `soulstream` streamable-HTTP server on `http://127.0.0.1:<MCP_INTERNAL_PORT>/mcp`, whose `Authorization` header is read from `PORTABLE_LOCAL_MCP_AUTHORIZATION` (the node token). No other MCP server, environment value, or API key comes from the orchestrator: the executor receives only the node credential and the release bundle.

## Version switch and supervision

Every `check_interval_secs` the launcher re-reads `current`. A new `source_commit` stages everything before the running child is touched: default config generation, payload install, clean-worktree check, runtime install, and `bind-release.mjs`. Every start rewrites the config generation it is about to serve, so a restart that allocates a new MCP port replaces the old port in the same generation folder. A dirty worktree holds the switch and preserves the changes. After staging succeeds the child is stopped normally and the launcher exits 75; the shim starts the new launcher under the new lock, which stages, binds, and starts again. Any failure after re-entry (bind, child start) rolls back to the release recorded in `active-release.json` (the last one that actually started) and disables further updates in that launcher run. A failure during staging leaves the current child running untouched.

Unexpected child exits restart the same release after `restart_delay_ms`; Ctrl+C and terminal termination are forwarded and never restart. Every start only ensures the workspace folder exists; an existing workspace is left untouched and no workspace or common repository is fetched.

## Failure and response

Pairing expiry prints the expiry and exits without re-pairing. A revoked credential (401) stops the launcher and does not re-pair. Payload hash mismatch, unsafe archive entries, checksum failure, a bind failure, or a failed new start leave (or restore) the previous release and are reported. Missing `Git` or unsupported platform/architecture fails in the bootstrap with an explicit message. No GitHub token, `GH_TOKEN`, `GITHUB_TOKEN`, service bearer, or `ANTHROPIC_API_KEY` is written to the child environment; the child's bearer is the node token.
