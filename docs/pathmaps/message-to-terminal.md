# 메시지 도착에서 종단까지

## 단발 LLM 요청 (카드 #418, S1)

외부 서비스의 `POST /api/llm/ephemeral`은 `orch-server-ts/src/llm/ephemeral_llm_routes.ts`에서 서비스 Bearer와 strict 요청 스키마를 검증한다. `backend` 생략 또는 `codex`는 기존 `generator` → `CodexEphemeralExecutor`로, `antigravity`는 `antigravityGenerator` → `AntigravityEphemeralExecutor`로 흐른다. 안티그래비티 effort는 low/medium/high만 허용한다. `production.ts`가 두 실행기를 각각 생성하므로 동시 실행 한도 1은 백엔드별로 독립이다.

`config.ts`의 선택 설정 `AGY_CLI_PATH` → `llm/antigravity_cli_path.ts`의 PATH → HOME/.local/bin/agy 순으로 실행 파일을 찾는다. 파일이 없으면 서버는 기동하고 해당 백엔드 요청만 503 `ANTIGRAVITY_UNAVAILABLE`로 끝난다. 실행기는 호출별 임시 cwd에 schema와 로그를 두고, sandbox·stream-json·disable-slash-commands 옵션으로 agy를 실행한다. 정리한 환경과 사용자 입력 한 줄을 전달하고 stdin을 닫는다. 완성된 NDJSON result 줄을 받으면 시간 초과 타이머를 지우고 프로세스 그룹을 종료한다. close에서 exitCode 0으로 반환한 뒤 기존 parseOutput이 SUCCESS와 오류를 판정한다. result 없이 시간 초과되면 기존대로 자식 프로세스 트리를 종료하고 close를 기다린다. 임시 디렉터리는 실행 후 지운다.

NDJSON의 init.model과 최종 SUCCESS 결과를 읽는다. output_schema가 있으면 structured_output을 JSON 문자열로, 없으면 response를 content로 돌려준다. 응답은 기존 `{content, model, latency_ms, attempts, usage?}`이며 usage는 input_tokens/output_tokens다. result 오류·error_message 스텝·stderr의 429/RESOURCE_EXHAUSTED/quota/rate limit은 429 `ANTIGRAVITY_RATE_LIMITED`로 보존하고 재시도하지 않는다. timeout은 504, 깨진 NDJSON이나 SUCCESS의 누락 출력은 502 `ANTIGRAVITY_INVALID_OUTPUT`, 나머지 실행 실패는 502 `ANTIGRAVITY_EXEC_FAILED`다. 모델 폴백은 호출자 XOPS가 소유한다. 세션·러너·DB 기록 경로는 이 단발 요청에 관여하지 않는다.

## PAS 지금의 보고 (#270 R1/R2)

웹 R2의 판 수신은 `session-types`/`mappers`/`stream-events` → `buildSessionUpdates` → `useSessionStreamCacheSync`의 보고 투영 → `persistentReports`다. SSE는 세션 query hydration barrier와 독립적으로 먼저 판 identity를 기록한다. PAS list/get 응답은 요청 시작 때의 판 identity가 여전히 같은 경우에만 반영하며, 생략은 보존하고 []는 비운다.

PAS 전화면의 `PersistentSessionChatView(showReport)` → `PersistentReportProvider` → `PersistentReportDeck`만 보고를 켠다. 일반 column과 카드 overlay에는 표시하지 않는다. provider는 기존 선택 key·단일 답 receipt·임시 답을 소유한다.

담당이 카드 질문을 남기면 서버가 그 카드 소유 사용자의 판에 `cq_<질문ID>` ask 장을 만들어 기존 metadata 방송으로 내보낸다. 판에서 그 장에 답하면 서버가 카드 답으로 접수하고 `reason:'card_question_answered'` ACK를 돌려주며, 웹·앱은 채팅 echo를 기다리지 않고 그 요청의 pending 슬롯만 해제한다.

보고 답은 `usePersistentReportSend` → `setPendingChatSend` → `submitIntervention.context_items`로 직접 보낸다. 「제목: 선택지」와 `persistent_report_reply {key,option}`, 원본 장 identity를 세션별 pending 칸에 싣고 초안·첨부·되돌리기는 건드리지 않는다. see 장과 선택지 없는 열린 ask 장은 「제목: 확인했어」와 `persistent_report_closed {key,title}`만 보내고, 전송이 시작된 뒤 기존 인증된 PAS DELETE로 닫는다. 일반 입력창의 자유 답은 기존 `getMessageContext`의 정확한 일치 조건과 visible 문맥을 유지한다. 채팅 답 안의 1단계 단추는 기존 `appendGeneratedText` 경로다.

sending은 임시 answered, failed는 open으로 돌아간다. 실패 표시와 재전송은 기존 대화의 pending 말풍선이 맡고, 같은 답 또는 확인 글의 retry는 같은 ID/context를 유지한다. 다른 글이 sending이면 답과 확인 단추를 비활성화한다. 다른 실패 글이 남으면 scoped operations bridge의 기존 알림 줄로 안내하고 확인 글은 보고를 닫지 않는다. `pendingChatSends.persistentReportOperation`은 key·updatedAt·종류와 접수 결과를 기록한다. 직접 전송과 `useChatInputSend`의 대화 재전송이 같은 표식을 유지하고 성공 시 acknowledged를 적는다. `PersistentReportProvider`가 표식을 읽어 접수와 취소 요청 상태의 유일한 기억을 소유하며, 세션·key·updated_at이 바뀌면 그 기억을 지운다. 서버가 받은 뒤에만 취소 요청을 보이고, 「제목: 답을 취소합니다」와 `persistent_report_visible {key,title}`을 같은 전송 칸으로 보낸다. 취소 요청 보냄은 그 장의 `updated_at`이 바뀔 때까지 남는다. 메시지 ack는 기존 이벤트 정합으로 pending을 비운다. 서버의 새 판은 임시 답을 교체한다.

`use-persistent-session-geometry`가 공용 `calculatePersistentSessionLayout`에 웹 폭 0.8과 최소 뼈대 221을 전달한다. 말풍선은 초상 칸에 portal하고 그 밖은 대화 칸 위에 선다. `useReportDeckHeight`는 장의 자연 높이를 재고 누르는 동안과 가로 넘김이 끝날 때까지 높이 반영을 미룬다. pointerup은 누름만 풀고, 가로 넘김은 기존 scrollend에서 보고 장이 정해진 뒤 푼다. 바깥 focusin은 portal의 실제 덱 DOM으로 판정해 초점 기억을 끄며, 사라진 단추에서 body로 떨어진 초점의 복구는 유지한다. 말풍선에서만 제목·칩·맥락·하실 일을 함께 굴리고 맨 아래 넘김과 답은 고정한다.

「확인했어」는 see 장과 선택지 없는 열린 ask 장에만 보인다. 먼저 제목과 `persistent_report_closed {key,title}`만 기존 intervene 경로로 보내며, 다른 글이 보내는 중이거나 실패한 글이 남아 있으면 장을 닫지 않는다. 전송이 시작되면 기존 인증된 PAS DELETE로 장을 즉시 숨긴다. key별 원본 장을 대기에 기록하며 실패하면 그 key만 원래 순서로 복원한다. 최신 동일 key 발행본과 역순 응답 처리를 유지한다. 실패는 기존 알림 줄의 「보고를 내리지 못했어.」다. 번호 칩은 기존 `ReportCardLink`의 선조회와 수정 키 처리로 번호를 카드 ID로 바꾸어 내부 링크로 연다.

실화면 진입점: 대시보드 빌드 뒤 `pnpm --dir unified-dashboard test:e2e:pas-report`(PAS HTTP/SSE 한 경로, heavy_verify runner 사용). 운영 컴포넌트는 `/components`의 PersistentReportDeck 샘플에도 등록되어 있다.

> 범위 주석: REST·내부 세션 송신·노드 명령은 `TaskManager.addIntervention` 이후 하나의 경로로 수렴한다. 실행 시작은 DB owner를 선출하지 않고 exact runtime registration identity를 한 번 기록한다.

> 장부 경계: delivery bookkeeping 실패는 엔진 결과를 terminal error로 바꾸지 않는다. 실패 delivery를 `uncertain/dead_letter`로 남기고 level 40 로그를 기록한 뒤, 턴은 엔진 Result대로 닫는다.

> 20단계 Result 소유 판정: Result의 소유 UUID가 현재 활성 전경 턴의 `active.uuid`와 같으면, interrupt receipt가 그 입력을 `receipt_still_queued`로 바꿨어도 해당 턴의 출력과 개입 대기를 종결한다. 활성 턴 자신의 UUID가 아닌 입력은 기존 원장 상태 판정을 따르므로, `still_queued`로 살아남은 continuation의 Result는 detached로 처리한다.

## PAS 전화면 웹 진입

`App`의 `/persistent`와 `/persistent/:sessionId`는 `PersistentSessionScreen`을 lazy로 연다. 홈 툴바의 초상 입구와 기기별 시작 선호도 같은 주소를 `navigateDashboard`로 연다. 인증은 기존 `main.tsx`의 AuthGate를 통과하고, 일반 대시보드와 PAS의 lifecycle은 함께 마운트하지 않는다.

`PersistentSessionScreen`은 PAS 목록으로 대상의 영구 세션 여부를 확인한 뒤 `resolveSessionForOpen`의 대상 ID 조회로 summary를 받는다. `activateRunSession`의 summary → 활성 세션 → 탭 순서 다음에 `PersistentSessionChatView`를 마운트한다. 상세 stream은 기존 `useSessionProvider` 한 벌이고 cursor scope는 origin과 이메일이다. 다른 PAS나 홈으로 이동하면 기존 cleanup이 이전 구독을 닫는다.

전송은 원고형 `ChatView`의 기존 `ChatInput` → 세션 개입 경로를 그대로 쓴다. 입력과 업로드는 소유 노드의 연결 상태로 제한하고 `/api/attachments/sessions?nodeId=<encoded nodeId>`를 쓴다. 표시·모션의 토글은 `usePersistentSessionDetailsController`의 즉시 저장과 활성 세션 표시 설정 투영을 재사용한다. 설정창과 카드 상세 오버레이는 대화 마운트와 활성 ID를 유지한다.

채팅 UI의 상태는 공통 `ChatViewContent`가 `ChatStoreScopeProvider` 안에서 읽은 `activeSessionKey`로 붙인 `ChatUiControllerProvider`에 있다. 일반 column, PAS 전화면, 다른 세션 overlay 모두 같은 owner를 쓴다. UI의 초안 추가는 전송을 호출하지 않으며 기존 입력창의 초안만 바꾼다.

## Antigravity 실행 경로 (PR A)

프리셋 backend의 정본은 `packages/model-catalog/src/index.ts:MODEL_BACKENDS`다. 노드 등록 wire의 backend enum과 러너 snapshot은 이를 받아 `antigravity`를 전달한다. 계정 잔량 공급자 연결과 화면 라벨은 PR B에서 이어지며, PR A의 광고 `usage_provider`는 null이다. 운영 활성화는 두 PR 이후다.

```text
모델 프리셋 → task/task_model_preset.ts:effectiveTaskBackend
 → task/task_turn_input_builder.ts:prepareNewTaskTurnInput (systemPrompt 분리)
 → task/task_engine_turn_runner.ts:executeTurn (native ID 재개)
 → runner/runner_child_engine_factory.ts:createRunnerChildEngine
 → engine/antigravity/adapter.ts:executeFrames
     새 대화: 홈/.gemini/config/agents의 이름별 정의, --agent만 전달
     정의 본문=시스템 지시(첫 턴의 빈 지시도 문자열), 26개 도구+세션 MCP
     재개: --conversation ID, 정의/--agent/--add-dir 없음
     한 프로세스: stdin user NDJSON 한 줄 + EOF, --log-file 세션 상태 경로
 → events.ts:accept (session/글/도구), terminal (complete 또는 error)
 → runner SQLite outbox → orch events JSONB → 기존 SSE/도구 표시/턴 사용량 MCP
```

`init.conversation_id`는 기존 `session.session_id` 이벤트와 `sessions.claude_session_id` 저장 경로를 사용한다. MCP 이름은 Codex와 같은 `mcp/<서버>/<도구>`이고 도구 ID는 native ID+턴 UUID+step index다. 시스템 지시와 MCP는 대화 생성 시 고정된다. HTTP는 headers를 보존하고 내부 MCP 주소와 세션 ID 헤더를 기존 helper로 구성한다. stdio는 command/args/env/cwd를 전달하며 SSE는 서버 이름만 warning 로그에 남기고 제외한다.

`task_running_intervention_transition.ts:tryIntervene`의 non-Claude 분기가 사람·에이전트·완료 보고를 모두 `intervene`으로 보낸다. 어댑터는 agy 프로세스 그룹에 SIGINT를 보내고 `not_delivered / interrupt_then_next_turn / next_turn_required`를 반환한다. init 이전 요청은 init 직후까지 신호를 보류한다. 실제 중단 직전에 /proc 자손 PID/starttime을 기록하고 close 뒤 살아 있는 동일 identity 자손에만 SIGTERM을 한 번 보낸다. complete/error 없이 스트림을 닫으며 제품 코드에는 종료 대기 루프나 SIGKILL을 추가하지 않는다. 호스트 장벽과 `task_turn_loop_transition.ts:resolveTurnLoopTransition`이 개입 큐를 다음 execute로 잇는다. 별도 전달 정책과 receipt metadata를 추가하지 않는다.

`events.ts`의 모델 DONE step 합만 턴 사용량이다. input_tokens는 input+cache_read, cached_input_tokens는 cache_read, output_tokens는 output, reasoning_output_tokens는 thinking이다. `init.model`을 종료 이벤트에 싣고 대화 누적 result.usage는 사용하지 않는다. 예상 중단에서 관찰한 합은 어댑터 메모리에 보관해 다음 complete/error에 한 번 더한다. 러너가 교체되면 미발행 누산분은 사라진다. total_tokens/context_usage/비용/first_call은 생성하지 않는다. 기존 `turn_usage_mode` 표시와 내부 `list_turn_usage`가 같은 complete/error를 소비한다.

안티그라비티 계정 잔량은 기존 `UsageSummaryService`의 5분 수집 → `provider_usage_get` → 워커 `auth/antigravity_usage.ts` → 모델 없이 `agy /usage` → `ProviderLimits` → `/api/usage/summary` → 프리셋 `weekly_headroom`으로 흐른다. 수집기는 Gemini Models의 weekly/5h 창만 7d/5h quota로 옮긴다. `model_catalog.ts`는 backend가 antigravity인 프리셋을 usage_provider=antigravity로 광고하며 기존 가용 판정과 주간 여유 계산을 사용한다. orch는 연결 노드의 `supportedBackends`에 antigravity가 있을 때만 그 공급자를 요청한다. 광고하지 않은 노드는 Antigravity 요청 없이 not_configured와 빈 quota를 채우며, 공유 계정의 비대표 노드에서도 Claude/Codex 수집을 유지한다. 전체 스냅샷 응답에 이 공급자가 없는 경우에도 파서가 같은 빈 결과로 채운다. 광고한 노드가 반환한 공급자 error는 그대로 보존한다.

수집은 기존 러너 상태 루트에서 고정 `antigravity-usage.log`를 호출마다 덮어쓰며 같은 루트를 cwd로 쓴다. 기존 공급자 예산의 AbortSignal로 자식을 종료하고 stderr 원문은 보관하지 않는다. 안티그라비티 성공 complete는 Claude result나 Codex turn/completed가 아니므로 기존 거부 기억을 해제하지 않는다. 새 한도 오류 코드는 추가하지 않으며, PAS 주간 게이지에는 Antigravity 줄을 추가한다.

계정 사용량의 독립 Gemini 수집과 요약 키는 제거했다. 옛 워커 snapshot의 extra gemini는 orch 입력 경계에서 무시한다. Gemini 모델 이름과 agy의 Gemini Models·antigravity:gemini:* 버킷은 유지하며, 상세 창은 5시간→7일 순서다. 주간 계산은 window 식별자와 weekly 필드를 사용한다. 공통 weeklyUsageGauges는 Antigravity를 마지막에 더하고 웹/iPad는 값 행이 하나 이상이면 빈 슬롯 없이 해당 줄 수만큼의 높이로 아래 정렬한다. 값 행이 없는 불러오는 중·조회 실패·주간 한도 없음·수집 대기는 기존 세 줄 자리와 안내를 유지한다. iOS 위젯은 optional Antigravity를 같은 순서로 읽으며 medium은 네 행 이상일 때만 두 칸 두 줄로 배치하고, 세 행 이하는 기존 세로 배치와 긴 남은 날 표기를 유지한다. small 네 행은 ViewThatFits의 세 후보로 표시한다.
