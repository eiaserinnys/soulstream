# 합친 훑기

카드 #1218 합의(설계 넷째 판)가 파이썬 손 모형으로 하던 합친 훑기를 soul-server-ts의 시험으로 옮겼다(카드 #1266 U5c). 손 모형은 분석 근거로 남고, 제품 완료의 근거는 이 시험이다. 숫자의 정본은 시험이 찍는 값이고, 아래 숫자는 이 문서를 쓴 때(origin/main `4156d14a`)의 값이다.

- 세계: `soul-server-ts/tests/task/state/combined_sweep/`
- 시험: `soul-server-ts/tests/task/state/card1266_combined_sweep.test.ts`
- 원본 모형: 카드 #1218 합의 폴더의 `fable_r2_machine.py`(아래 「M」)

## 무엇을 훑는가

한 세션의 서버 줄, 노드 실행, 러너, 두 통로를 합친 구성 하나를 상태로 두고, 처음 구성에서 넓이 우선으로 닿는 구성을 모두 훑는다. 구성은 M과 같은 열다섯 칸이다.

| 칸 | 뜻 |
| :-- | :-- |
| S | 서버의 세션 줄(시작 중, 다시 띄움, 한도 재개, 등록됨, 끝남, 한도 끝남, 베낀 끝남, 끊김 중단, 묻힌 끝남) |
| W | 한도 재개 예약 |
| L | 노드와 서버의 연결(목록 맞추기의 단계 포함) |
| ch | 통로 하나의 사건 줄(길이 K) |
| ex | 노드의 실행 |
| q | 받은 지시 |
| p, life, tail | 러너 프로세스, 러너 수명, 서버에 닿지 않은 기록 |
| l2, d2, u2 | 통로 둘의 소켓과 양방향 줄(길이 K2) |
| wt | 워크트리를 다른 활성 세션이 쓰는가 |
| nt | 완료 전달 의무 |
| st | 받아들인 사람의 멈춤 |

걸음은 M의 42개(J01~J45, J12, J30, J40은 M에도 없다)다. 셋째 판의 안에서는 J34(재정렬)가 I1 고침으로 일어나지 않아, 나머지 41개가 모두 한 번 이상 쓰이는지 시험이 본다.

### 제품 판정 함수를 부르는 걸음

노드와 러너의 걸음은 짝이 있는 한 제품 판정 함수로 다음 구성을 고른다. 걸음이 일어날 수 있는 조건은 M을 따른다.

| 걸음 | 판정 함수 |
| :-- | :-- |
| J01 지시가 온다 | `projectNodeExecutionPhase`, `decideNodeRequest` |
| J07 사람이 멈춘다 | `decideNodeRequest`, `decideNodeStopRequest` |
| J08 멈춤이 정리된다 | `stepNodeBarrier` |
| J19 사건이 서버에 닿는다, J35 영구 거절된다 | `decideNodeResponse` |
| J27 결과를 받는다 | `decideNodeInstruction` |
| 넘기던 지시를 잃는 걸음(J14, J15, J16, J19, J31, J32, J41) | `decideNodeInstruction`(번호로 물음) |
| J15 복구 훑기 | `decideRunnerRecovery`, `decideRunnerHandle` |
| J45 주기 중앙 확인 | `decideRunnerCentralCheck` |
| J26 러너가 명령을 받는다, J28, J29 엔진이 끝낸다 | `decideRunnerLifecycleStep` |

짝이 없는 노드 걸음(J02~J06, J09~J11, J13, J16, J17, J41, J42, J44), 러너 걸음(J32, J33, J43), 서버와 연결 걸음, 통로 걸음은 M에서 옮겼고 걸음마다 M의 줄을 주석으로 달았다. 판정은 입력 키 캐시를 거친다. 캐시 없이 길이 1과 1은 4.3초, 캐시를 쓰면 1.1초다. 시험이 캐시가 판정을 바꾸지 않음을 본다.

서버 걸음은 orch의 `decideSessionTransition`을 부르지 않고 M에서 손으로 옮겼다. 그 함수는 세션 줄 하나의 상태 값만 받고 한도 재개 예약은 읽기 전용 투영이라, M의 서버 상태가 가르는 한도 끝남, 베낀 끝남, 묻힌 끝남과 예약을 담지 못한다. 거절 사유는 orch의 판정 순서와 와이어 사유표를 따랐다. 워크트리 점유가 종료 상태 검사보다 앞서고, `terminal_without_resume`은 `already_terminal`로 실린다.

  - 7: 서버가 도는 중으로 적었는데 노드에 주인도 러너도 없는 세션은 닫히거나 다시 맡아진다.
  - 9: 알림이 필요한 종료가 서버에 적히면 완료 전달이 등록된다.
  - 12: 러너가 적은 끝남은 서버의 종료 기록에 닿는다.
  - 13: 받은 지시는 적용, 반환, 모름 가운데 하나로 끝난다.
  - 14: 서버가 끝남으로 아는 세션의 도는 러너는 되살려지거나 거둬진다(엔진 걸음은 스스로 하는 일로 세지 않는다).

- 걸음 셈: 넘긴 지시가 두 번 들어갈 수 있는 걸음(dupHandover), 멈춤이 사라지는 구성(vanishedStop).

스스로 하는 일은 시스템, 시각, 엔진의 걸음과 끊긴 연결이 다시 붙는 것(J22)이다. 길이 있음은 스스로 하는 일로 목표에 닿는 길이 하나라도 있는가이고, 공정하면 반드시는 스스로 하는 일로 길 없는 구성에 빠질 수 없는가다. 위반이 나오면 시험 메시지에 위반 구성 하나의 최단 경로가 실린다.

### 워크트리 점유 거절의 고침 (카드 #1266 U5c)

처음 옮겼을 때 제품은 다른 세션이 워크트리를 쥐어 잇기가 거절되면(`worktree_busy`) 다시 될 수 있는 거절로 보고 러너를 거두지 않았다. 그 칸 하나에서 길 13이 624, 길 14가 2,208, 영구 거절 없이 닿는 길 15가 384 나왔다. 설계 design.md:101의 「거둠을 빼면」 숫자와 같다.

- 약속 14의 최단 경로: 러너가 뜬다, 실행 등록이 서버에 닿는다, 서버와의 연결이 끊긴다, 유예가 지난다, 러너가 실행 명령을 받는다, 다른 세션이 워크트리를 차지한다.
- 약속 13의 최단 경로: 지시가 온다, 러너가 뜬다, 노드가 재시작한다, 유예가 지난다, 다른 세션이 워크트리를 차지한다.

담당 판정으로 제품을 모형에 맞췄다. 점유는 다시 될 까닭이 없는 거절이다(`node_adopt_rejection.ts`). orch는 기록된 끝남보다 점유를 먼저 보므로, 노드는 거절을 받으면 중앙 세션 줄을 읽어 가른다(`centralSessionFactsOf`).

| 중앙 세션 줄 | 모형(M:406-412) | 제품 |
| :-- | :-- | :-- |
| 끝남이 기록됨(종료 사건 번호 있음, 또는 서버가 스스로 닫은 끝남) | 러너만 은퇴 | 러너 거둠 |
| 끊김 중단(종료 사건 없는 interrupted) | 러너를 거두고 오류 종료를 올림. 서버는 끊김 중단에 닿은 종료를 받아 끝남으로 적는다 | 러너 거둠과 오류 종료 |
| 읽지 못함 | (없음) | 러너 거둠만 |

「준비 안 됨」(`worktree_not_ready`)과 사유 없는 옛 서버 거절은 다시 될 수 있는 거절로 남아 거두지 않는다.

## 알려진 한계: 약속 15

영구 거절에서 나오는 약속 15는 설계가 받아들인 한계다. 사람의 멈춤으로 올린 종료가 영구 거절되면 세션은 「멈춤」이 아니라 「끊김 중단」으로 닫힌다. 표시만 다르고 다시 시작할 수 있다. 시험은 약속 15가 0보다 크고, 영구 거절 걸음을 끈 세계에서 길과 공정 판정이 모두 0임을 단언한다. 영구 거절은 스스로 하는 걸음이 아니므로, 그 걸음을 끈 세계의 위반이 곧 그 걸음을 거치지 않고 닿는 위반이다.

## 모형과 다른 점

- 잇기 거절의 사유 순서: orch는 워크트리 점유를 끝남 검사보다 먼저 본다. 그래서 기록된 끝남에 점유가 겹치면 `worktree_busy`가 실린다. M은 끝남을 먼저 본다. 세계는 orch 순서로 사유를 내고, 잇기 거절의 판정에 중앙 줄의 끝남 기록(S가 기록된 끝남인가)을 넘긴다. 제품이 그 칸에서 M과 같은 처분을 낸다.
- 거둠의 때: 제품은 잇기 거절을 받은 뒤 다음 훑기의 중앙 확인이 러너를 거둔다. 세계는 거절을 받는 걸음에서 곧바로 거둔다(M과 같다).
- 종료 거절의 기록 비교: 세계는 이미 기록된 끝남에 닿은 종료를 늘 「다른 종료」로 판정에 넘긴다. 그래서 제품의 「같은 종료가 이미 기록됨, 적용됨」 칸은 실행되지 않는다. M은 그런 종료를 거절로 보고 등록을 은퇴시킨다. 제품이라면 같은 종료를 다시 올린 구성(2,076개)이 완료 전달 등록까지 갈 수 있다. 그래서 I3 되돌림의 길 9 숫자는 제품과 다를 수 있다.
- 상수로 부르는 판정: J08 멈춤 정리(`stepNodeBarrier`)와 J28, J29 엔진 끝남(`decideRunnerLifecycleStep`)은 판정을 고정된 입력으로 불러 적용 여부만 확인한다. 다음 구성은 M을 따른다.
- 사람의 멈춤(J07): 제품은 넘기기를 기다리는 멈춤(`stop_after_handoff`)과 곧바로 멈춤(`stop_now`)을 가른다. 세계는 둘 다 곧바로 멈추는 중으로 보낸다. M에 넘기기를 기다리는 동작이 없어서다.
- 넘기던 지시의 판정: 세계는 같은 등록의 러너가 답했는가(u2)만 보고 적용됨 또는 적용 안 됨을 넘긴다. 러너가 죽거나(J31) 노드가 재시작한(J14) 경우 제품의 정의로는 「모름」이지만, 세계는 「적용 안 됨」으로 넘겨 다시 보낸다. M과 같은 결과다.
- 실행 등록의 거절: 제품은 칸과 상관없이 붙인 러너를 닫는다(`abandonRejectedAttempt`). M과 같은 결과다.
- 영구 거절(J35): 칸은 `decideNodeResponse`가 내고, 영구 거절이나 격리 칸이면 M대로 소유를 놓고 목록을 다시 보낸다. 칸의 중앙 오류 표시는 목록 다시 보냄으로 둔다.
- 복구 훑기(J15): 제품의 조치 판정은 물어봐야 아는 칸(백그라운드 보유, 만료 보유 해제, 붙은 종료 은퇴)을 거친다. 세계는 그 물음에 구성으로 답한다(정상 보유면 보유 중, 아니면 없음과 해제됨).
- 주기 중앙 확인(J45): M은 노드가 턴을 도는 중이고 중앙이 활성이 아닐 때만 보낸다. 세계는 연결, 살아 있는 러너, 보낸 잇기 없음만 보고 나머지를 판정에 맡긴다. 직전 잇기 응답은 늘 「없음」으로 준다(모형은 주기마다 새로 판정한다).
- 러너의 실행 명령(J26 EXEC): 제품 수명 기록은 끝난 기록도 새 실행 명령으로 다시 연다. M은 실행 전과 완료 끝남에서만 연다. 셋째 판의 안에서 둘이 갈리는 구성에는 닿지 않는다(구성 수가 같다).
- 시동 복구 잇기와 붙은 러너 잇기는 구성이 가르지 않는다. 세계는 두 호출의 칸이 같은지 걸음마다 확인한다.
